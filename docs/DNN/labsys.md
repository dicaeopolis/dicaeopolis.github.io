```python
training_data = datasets.FashionMNIST(
    root="data",
    train=True,
    download=True,
    transform=v2.Compose([v2.ToImage(), v2.ToDtype(torch.float32, scale=True)])

test_data = datasets.FashionMNIST(
    root="data",
    train=False,
    download=True,
    transform=v2.Compose([v2.ToImage(), v2.ToDtype(torch.float32, scale=True)])
)
```

Well, well, well... 尽管有些对数据效率上心的教程会告诉你应该开 num_workers 和 pin_memory，但也就那样了，不是吗？

在比较新的 PyTorch 教程上面，还会给出 https://docs.pytorch.org/tutorials/intermediate/intermediate_data_loading_tutorial.html 这种数据效率优化方案。（比如说它里面也提到了 prefetch 但是相对后文聊到的东西，这个 prefetch 的视野太窄了）

但事实上，1）先验上：优化开关并不是开了就能理所应当地变快 2）后验上：很多细节也需要进行各种 Profiler 之后才能确定。

实际上大部分初心者向的训练教程和网上的各种代码还是在教你写 demo 代码：

用 dataloader 加载训练集，监控训练 steps 和 epoches 并调度学习率，然后做前向和反向传播并处理多卡的数据同步，再按周期加载 dev 集合对模型的泛化状态进行监控和早停，并更新 best.ckpt；最后再对训练得到的最优结果在 test 集合上面进行推理，记录并聚合指标。

这样说是有明确原因的，就在我写这个文章的半路，我让 GPT-6.1 Sol 检查了一下自己的代码，它显然没有接住我的需求，尽管我实现了一个初步的调度器，它还是拿这个调度器当作 DataLoader 的 alias，代码依旧是同步的逻辑。因为这方面高效的训练语料太少了。

## 欢迎来到现实世界

上面这个流程很原理化，也很典型，但是就性能上看，明显存在好几个性能上有待细细考虑的事情：

1. 怎么加载训练集，就 OpenWebText 来看，数 TiB 的语料，除非实验室的老板比较慷慨，一般而言这种数据集都是存在本地的 HDD 上面的，如果你要对短序列训类似 BERT 的模型，随机抽数据组 Batch 对于 HDD 是灾难性的。——需要消灭随机读写。

2. 对于变长序列的前向和反向传播，终究要整理到 [B, L, ...] 这样的 tensor 里面，但是每一条序列的真实长度本身是不一致的，需要做 padding。但这带来了一个明显的 Trade-off： padding 变多，无效计算变多；padding 变少，并行度下降。——需要寻找综合效率的甜点，并根据显存预算组 batch，然后对应的调整有效学习率。关于学习率缩放，苏神的博客已经探讨非常详细了：https://kexue.fm/archives/11260

3. 训练本身的动态是相对稳定的，考虑一个情况：磁盘一直空闲，非要等到模型训到对应 step 再加载 dev，那为什么不提前预测到对 dev 的需求，在空闲时提前加载 dev 呢？——需要构建训练流水线。

4. 类似的，大部分这种 demo 代码都是同步的写法，也就是发现 dev 出了更优的模型，就存模型，但“存模型”这个事情本身**把训练进程阻塞**了。参看上一条，本质上是同步的代码逻辑，让各种训练无关的事情阻塞训练了。——1）需要调度器处理读写冲突，尤其是一边加载数据（随机读）一边保存模型（顺序写）这样的冲突 2）需要进行异步化改造，让无关任务不阻塞训练。

## Rethinking Infrastructure

### 消灭随机读写

Stop torturing your HDD. 一个典型的数据集是 Mega 或者 Tera 级别数量级的 Kilobytes 小文件，我们遇到的第一个 Trade off 来自训练动力学和硬件之间的张力：基于batch统计梯度的优化器需要足够好的随机性以得出合理的梯度估计，而 HDD 痛恨随机性。

因此需要一个折中的方案：例如，我们把数据像 CD 音轨一样，连续打包为 512 MiB ~ 4 GiB 这样的包（shard），每次随机加载（HDD -> DRAM）一个 shard 并送去训练，在训练的过程中（DRAM <-> GPU/VRAM），还可以预先加载（prefetch/staging）好下一个 shard （HDD -> DRAM）；如果分片大小设计得当，比如说，加载好一个shard的时间刚刚好隔壁GPU训练完，那就能正好补上。

也就是流水线的思路，当然高大上一点可以叫做 Dataset Sharding & Staging。

假设每个 shard 大小是 512 MiB 而推理效率和数据加载效率可以预先 profile 出来，由此可以决定每次 prefetch 的时候读多少个 shard 进来，以尽量减少流水线气泡。

当然这会牺牲随机性，但是实测，**不会训炸**。

哦对了，以上推导仅限单任务。多任务还按照这个方式就会产生数据争用了，详见下文。

### 处理填充与并行度的矛盾

首先 fuck the world，音频模型统一填充到 4s 我觉得是相当荒谬的。不同语言的一句话常见长度各有区别，不能因为自己的 infra 能力低下就硬在这里凑 batch。古代技术滚一边去。

我们先介绍一个实现上很简单的贪心思路。考虑显存预算支持长度为 $L$ 的序列进行推理，那么必然满足约束 $B \times L_B \le L$，其中 $B$ 是批大小，$L_B$ 是批内对齐后的长度；对于一组长度不一的数据 $L_i$，我们从长到短排序，然后找到 $j$ 使得 $j \times L_0 \le L$ 即可把后 $j$ 个数据组成一个批次。

这就是 fairseq 的思路。果然思而不学则殆，感谢 Gemini 老师帮我查到了出处，这个本来是我自己想的，结果没想到有库已经在用了。

不过，老实 padding，很枯燥吧？

让我们更细致一些，思考下面的 demo：

1. 对于最简单的 MLP 层，我们考虑一个 $[B, L, D]$ 的 tensor，送进一个 $D\times F$ 的矩阵，得到 $[B, L, F]$ 的输出 tensor。

2. 再考虑一个 $[B\times L, D]$ 的 tensor，送进一个 $D\times F$ 的矩阵，得到 $[B\times L, F]$ 的输出 tensor。

3. 注意到，我们本身就能对 $[B, L, D]$ 的 tensor 堆叠成一个 $[B\times L, D]$ 的 tensor，送进一个 $D\times F$ 的矩阵，得到 $[B\times L, F]$ 的输出 tensor，再拆开得到 $[B, L, F]$ 的输出 tensor。

4. 现在，思路就打开了：我们考虑 $B$ 个 tensor，每个都是形如 $[L_i, D]$ 的 tensor，我们要并行地计算每个 tensor 对 $D\times F$ 的矩阵的乘积，那么我们可以把所有 tensor 首尾相接，得到一个 $[\sum L_i, D]$ 的 tensor，再乘以矩阵，就可以得到 $[\sum L_i, F]$ 的输出 tensor，然后按照原顺序拆开即可。

由此，我们**消灭了padding**！！！

（说句题外话，让 LLM 审读的时候基本上所有 LLM 对这句话都表达了相当的恶意，觉得我是在 overclaim。果然我们的 LLM 真是油光水滑四平八稳的老油子，对这种戏谑的修辞是一点看不懂啊……）

然后，还有一些比较重要的问题需要处理，比如说做 1-D CNN 的时候，卷积核不能跨音频边界，需要做处理；以及 sdpa 的位置编码也得改。但是对于各种投影计算的大头，是能几乎消解 padding 的。

这就是基于 ragged tensor 的现代技术。

现在阻碍我们的就是显存的物理上限了。

### IO 事务化调度

前面铺垫了这么多，其实 IO 事务化调度的思想已经呼之欲出了。我们考虑下面的数据通路：

```
DRAM /dev/shm 128 GiB <-全双工，高速-> SSD /dev/nvmex 256 GiB <-半双工，低速-> HDD /dev/sdx 4TiB
```

我们可以抽象出两种事务：

1. 读事务，包括加载 shard，加载 ckpt 等；

2. 写事务，包括保存 ckpt 等。

一个很关键的观察是：**训练动态是高度确定性的**。我们可以把每个请求分为：

1. 我需要尽可能在某个时间前把数据准备好，一般而言是把数据读入内存。例如按 shard 进行训练或者推理的时候，我知道这一批 shard 的训练或者推理需要花 1h，我就在开始推理的时候发出请求：T+1h 之前，需要尽可能把下一个 shard 的数据准备好。

2. 我需要执行这一数据操作，因为前序依赖满足了，尽管这些依赖不一定可以预知完成时间，但现在我发出请求了，我希望能尽快执行。例如早停时，加载 best.ckpt 进行最终的 eval，因为不可能预知多久早停，所以我只能在早停触发后发出这个请求。又或者，每次在刷新 dev 后写 best.ckpt 的操作，因为只有等 epoch 训完才能出 best.ckpt，所以也是这一类。

也就是分为前瞻性(ahead-of-time)事务和即时性(immediate)事务。

这样我们就可以笛卡尔积得到四种基本事务：前瞻的读、前瞻的写、即时的读和即时的写。

为什么要这样区分，而不是用简单的“处理这个shard的同时加载下一个shard”这种训练流水线呢？很简单，我们考虑两个训练进程，它们在同一数据集上以稍有不同的设置训练同一个模型。如果两个模型都按照这个简单的流水线调度逻辑，那么在训练开始时，就会发生严重的数据争用，两个进程在加载同一个起点的 ckpt；如果种子是一样的话，还可能加载同一份 shard。并且后续的训练动态如果近似同步，则几乎每一次加载shard都会出现数据争用。

但是如果我们把两个训练任务都接入这个IO调度器，理想的调度情况应该是：

```
进程A提交即时的读事务1，加载模型ckpt(HDD->SSD->DRAM)
进程B提交即时的读事务2，加载模型ckpt(SSD cache hit, SSD->DRAM)
进程B提交即时的读事务3，加载第一个数据分片(HDD->SSD->DRAM)
进程A提交即时的读事务4，加载第一个数据分片(HDD->SSD->DRAM) <-- 此时磁盘忙于事务3，事务4排队，不能争用磁盘。
........
```

还有一个比较重要但也很自然的约束：同类重复性事务的第一次运行，如果不能从历史数据里面读出参考数值，就应当是即时性的。比如说“加载dev集合”这个事务，在模型第一个 epoch 训练完之前，它是不知道1）自己要加载多久 2）epoch要训多久。而这一事务的被即时性提交运行后，所谓“冷启动”，就能获取到自己的任务耗时，然后后面提交第二个或更后的 epoch 训练任务，就能有现实依据地给出前瞻性任务的耗时了。

并且我认为在设计上，前瞻性事务不能要求事务提交者给出明确的时间限制，因为这会要求提交者编写无帮助的 ETA 计算逻辑，我更希望事务提交方的代码专注于自己的执行流和依赖，或许一个比较好的交互方式是依赖具体阶段的时间戳，比如说 dev_start 标定验证集开始推理，然后明确 dev_load 的这个读事务需要在 dev_start 之前完成；而 dev_start 本身可以通过训练状态的进度回调和相关 ETA 计算出来。还有一个重要的要求是，任务一旦知道未来会需要某个对象，就立即登记；调度器再决定什么时候搬运。不然，异步架构就退化成了阻塞等待数据的同步架构了。

并且很显然，在单个训练任务的情况下，这个架构很自然地退化成了异步的训练流水线。可以说它是一个训练流水线在多任务情况下的一种拓展。

下面就存在几个问题：

1. 怎么在这个事务模型下面实现这个调度器，使得在满足容量和持久化约束的条件下，能够减少各计算阶段等待输入的时间，并兼顾公平性。
2. 前瞻性任务依赖某类重复性任务的计时，如何把这种“重复性”抽象出来，并让性能数据能正确落地？
3. 怎么编写代码，来利用好这个基建？

好吧，借助前人的力量，我让 Gemini 大人查了查论文。查到了比如说：[NoPFS](https://arxiv.org/abs/2101.08734) (Dryden, et al; ETH Zurich; SC'21) 、 [CheckFreq](https://www.usenix.org/system/files/fast21-mohan.pdf)（Mohan, et al; UT Austin; FAST'21）、[HEFT](https://ieeexplore.ieee.org/document/11044792)（Kulagina, et al; Humboldt-Universit¨at zu Berlin, Germany; CCGrid'25）等文章。然后给 GPT 大人读了一下，我自己也审查了一遍，大体上可以给出下面的方案：

1. 对训练或者推理进程而言，首先需要把所有 IO 任务事务化，也就是依赖这套 IO 中间件的 API 进行处理，换句话说就是“使用即接受统一管理”，不能手写绕过；他人的进程不使用这套中间件，就无权干预他人任务。其次这套中间件无法约束的一点就是自己代码逻辑写得烂，前瞻事务只有真正前瞻地提交，才可能被调度感知到而产生预取收益，也就是前面的“任务一旦知道未来会需要某个对象，就立即登记”。当然现在是 Agent 时代，让 Agent 写好后自查一下就行了。

2. 对调度器，首先算好 ETA 是重中之重，合理的 ETA 估算一方面可以给进度回调提供透明的数值，另一方面也可以合理排期。那咋排期呢？任务又耗时有依赖，是一个 DAG，我们可以考虑用最晚启动时间的算法来安排每个任务。

大体上就是这个方法，具体到实现上还有很多细节，由于摸出前面这一大坨就花费了我很多精力，细节我就懒得写了。我说，读者把这个文章直接喂给 AI 让它对组里面的服务器做类似的性能分析并思考相关改动，也不失为一种提示词工程。不过当下更时新的说法叫做 skill 罢了。
